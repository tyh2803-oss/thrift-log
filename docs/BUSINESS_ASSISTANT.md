# Private business assistant

Thrift Log now uses a reasoning model and typed tools for natural conversation. It searches the signed-in user's records, answers questions using the existing financial calculations, reads private attachments and prepares edits in the existing review cards. It has no tool that saves business records. The user still chooses **Approve All** before the canonical approval endpoint commits a batch.

## Minimum setup and release procedure

1. With approval, apply **[202611130001_assistant_conversations.sql](../supabase/migrations/202611130001_assistant_conversations.sql)** once in the existing Supabase project's SQL Editor, or through the existing migration workflow. It requires the invite-only beta migration (schema 6 or later). It is also tested with schema 7 registration. This optional feature does not change the business schema version or require a second database.
2. Add server-only `OPENAI_API_KEY` to the Vercel environment that will run the feature. A key in Codex Cloud is not automatically copied to Vercel. The default model is `gpt-6.1-sol` and reasoning effort is `medium`. Optional overrides are `OPENAI_ASSISTANT_MODEL`, `OPENAI_ASSISTANT_REASONING_EFFORT` and `OPENAI_SCREENSHOT_MODEL`; a blank screenshot override inherits the chat model. The app never silently falls back to a different model. Keep the existing Supabase public/server variables; no new Supabase credential is needed.
3. Deploy the reviewed code only after approval. Open Assistant while signed in and confirm business chat is ready. Test a business question, a PDF/CSV question, and a sale proposal against an intended test record. Confirm that no sale exists before approval and that exactly one exists after approval/reload. Check a second authorized account sees its own conversation and sources. Existing file imports remain available if optional chat setup is absent.

**Approved rollout, November 13:** migration `202611130001` has been applied transactionally and recorded in the existing project. Hosted readiness, private bucket/RLS/RPC protections and isolated service reads passed. Pre/post fingerprints confirm existing business, Auth, beta-access and photo records were preserved. Existing Whatnot sync metadata continued updating independently. No production Auth settings or existing storage objects were changed. Do not replay the migration. Check the deployment's server-side configuration; never put the OpenAI or Supabase server key in a `NEXT_PUBLIC_` variable.

The migration is additive: two private tables (`assistant_conversations`, `assistant_files`), service-role-only `assistant_chat` and `assistant_file` RPCs, a private readiness helper, and the private `assistant-files` bucket with a restrictive server-proxy policy. It neither rewrites existing workspaces nor alters Auth UUIDs, beta authorizations, financial constraints or existing photo policies. Conversation/file endpoints fail closed if their tables, private bucket or storage policy are misconfigured. Local migration tests preserve an existing owner's sale, inventory, photo references and financial data byte-for-byte under schema 6 and schema 7. Existing Whatnot features are independent and untouched.

For a staged rollout, apply the optional migration first while the old app continues running, then release the code. To turn off chat without affecting business records, remove its OpenAI key from that deployment or roll back the application deployment. Retained conversation/source data can remain private; do not drop business tables or delete Auth users. Disabling the key also disables AI image/document extraction; deterministic CSV and manual entry remain available.

## Everyday use

- Ask “How much did I make on Depop last month?” or “What do I still need to list?” The assistant reads canonical metrics and current physical inventory. Reporting dates and current pipeline snapshots remain distinct. Shared labor/overhead is labeled global instead of assigned to a marketplace without evidence.
- Use the iPhone keyboard microphone to dictate into **Message assistant**. No separate microphone permission or transcription service is required. For “I sold the Harley tee I listed on Depop yesterday for $35,” the assistant searches likely pieces, keeps the listing date separate from the missing sale date, and asks for the missing facts. Ambiguous matches show short selectable replies.
- Sale review keeps actual price, sale date, marketplace, seller fees and purchase cost together. Known inventory costs are reused. Blank costs/fees remain unknown; explicit zero is valid. **No other selling amounts ($0)** is an explicit confirmation, not a hidden default. Consequential sale/shipping reversals continue through the existing **Change status** workflow.
- Attach screenshots, photos, PDFs or CSVs and ask a question without importing. PDF and image bytes are read natively; CSV tools search rows and compute literal column totals in integer cents without executing formulas. Common buyer/contact columns are excluded from CSV model input. Other user-provided file content may still contain personal information.
- Ask to prepare a supported file import, then correct exceptions in review or in conversation. The assistant reuses the established extraction/CSV pipeline, preserves file source identity, and never skips incomplete physical rows to make a batch appear valid. Native known CSVs use deterministic amounts rather than model arithmetic. Unsold stock spreadsheets should use **Inventory → Import CSV** rather than becoming completed sales.
- Shared fees/date corrections update pending rows. Purchase allocations count unique new physical items, distribute leftover cents deterministically, protect known existing costs, and synchronize individual overrides across pending cross-listings. Approval remains required.
- **Refresh chat** reloads confirmed conversation context without discarding local draft edits. Interrupted responses can retry with a stable request identity. Failed follow-ups preserve the last completed draft checkpoint. Reopening the app or another device restores retained messages, sources and the last completed pending review. Approved receipt IDs prevent approved drafts being restored as unsaved work.
- **Clear chat** confirms removal of the private conversation, pending proposals and retained assistant source files. It does not delete approved inventory photos or business records. A cleanup failure is reported separately so the user can retry removing retained sources.

## Tools and boundaries

Read tools include inventory/listing/sale/history search, individual owned records, business and show summaries, pending draft review, owned inventory photo inspection, attachment reading/search and exact-cent CSV column summaries. Bounded pages and completeness flags prevent a partial page from being presented as a full dataset.

Proposal tools prepare existing-item sales/listings, unsold/archived moves, supported existing-order fulfillment/refund/return/cancellation events, file-import drafts, shared draft corrections and purchase allocations. They operate on cloned drafts, not the business database. They reuse the planner, ledger, operation retry protection, financial checks, explicit consequential confirmations, revision checks, durable receipts and atomic `commit_workspace` transaction. New physical inventory from files uses optional matching and explicit final approval; similarity and repeated identifiers do not block imports. Arbitrary text-only new inventory, consequential financial reversals remain in the established inventory/order editors. Saved acquisition costs can be entered through the explicit bulk cost dialog; its additive migration and rollout require separate approval (see [setup guide](IMPORT_REVIEW_AND_PURCHASE_COSTS.md)).

The model cannot choose an actor, run SQL/code, follow arbitrary URLs, browse the web, access another account, publish marketplace listings, change credentials or invoke a business-write endpoint. Server identity comes from verified Supabase Auth and live beta authorization, not a requested user ID. Tools read only a workspace loaded for that identity. File metadata is owner-scoped in the private schema; paths are derived and verified server-side. Raw storage access is denied to client roles, even when a permissive policy is present. The proxy checks live authorization and source hashes before returning file bytes. Revoked accounts cannot resume conversation, attachment or approval access.

OpenAI calls use the fixed Responses API endpoint with `store: false`. Reasoning items, including encrypted reasoning, are replayed only within the current tool loop and are not sent to the browser or persisted. Saved context contains final messages, bounded file/review metadata and the last draft response. API token usage is diagnostic metadata, never automatically recorded as a business expense. Record text and file content are untrusted data; tool schemas/ownership checks enforce the access boundary independently of model instructions. OpenAI API retention/data controls still follow the API account's settings; `store:false` is not a claim of zero provider retention.

## Practical limits

- Last **40 messages** per private conversation; this is bounded continuity, not unlimited ChatGPT history.
- Up to **10 turns per minute**, one active turn per workspace, optimistic conversation revisions and expiring leases. Clearing chat does not reset the rate limit.
- Up to **16 tool calls**, six model rounds, 30,000 output tokens and 150 seconds per turn. Tool data has a 22 MB turn budget. Large/multi-file requests may need smaller steps.
- **5 MB/file**, **16 MB/composer batch**, ten attachments; up to **200 retained private sources** per account until cleared. Only JPEG, PNG, WebP, unlocked PDF and CSV are supported. Export Excel/Numbers as CSV; arbitrary binary office formats and executable files are unsupported.
- General CSV questions support up to **5,000 rows**, paginated 30 at a time. Import review retains its existing **300 CSV rows**, 30 item rows per order, ten analysis parts and 30 extracted records per PDF limits. Header/source interpretation can still require clarification, particularly ambiguous dates, non-USD amounts or net-payout versus sale-price columns.
- Unknown or conflicting financial facts are not invented. Some accurate-looking imports remain pending until required sale facts are supplied. Estimates and partial sums are labeled accordingly.

## Verification

`npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `npm run test:history-browser` and the existing assistant/demo browser suites cover parsing, approval, matching, accounting, tenant isolation, private sources, migration compatibility, stale/revoked requests, retry, reload and narrow layouts. Browser tests use Chromium desktop/iPhone-sized emulation with isolated Auth/database doubles; SQL tests run in PGlite, not hosted production.

Opt-in `RUN_LIVE_BUSINESS_ASSISTANT=1 npm test -- tests/business-agent-live.test.ts` exercises real Sol with synthetic records only: matching and date clarification, follow-up fees, exact canonical profit, existing structured screenshot extraction, native PDF extraction and direct native PDF tool reading without import. It never loads or writes a hosted workspace. Cloud's test-only credential-proxy transport is confined to that test; the deployed app uses normal server fetch. Real seller-file acceptance and physical iPhone dictation/Safari testing remain manual.
