# Whatnot read-only connection

Each approved Thrift Log user connects their own Whatnot seller account in **Settings → Whatnot**. The connection uses Whatnot's documented personal access tokens (PATs), so no OAuth application, SMTP or shared seller credentials are required. Credentials stay encrypted on the server. No live seller account was available during implementation; API contracts, provider responses, credentials and webhooks were tested with synthetic fixtures. No production migration or business-data write was performed.

## Minimum setup in the existing projects

1. Back up the existing Supabase project and inspect its migration history. Apply **only** [202611120001_whatnot_read_only.sql](../supabase/migrations/202611120001_whatnot_read_only.sql) once, using Supabase SQL Editor or your normal migration workflow. This requires the existing invite-only beta migration (schema 6 or later); it also works with registration/schema 7. It adds three private tables and one service-role-only RPC. It does not change the schema version, Auth users, beta authorizations, business records, financial constraints or private-photo policies. Both schema-6 and schema-7 compatibility and preservation are covered by local PostgreSQL tests. Application deployment is safe before this step: the optional connection shows **Setup needed**, and existing workflows continue.
2. For synchronization while the app is closed, set **`CRON_SECRET`** in Vercel Production to a randomly generated secret of at least 32 characters, then redeploy the current code. `vercel.json` schedules a daily reconciliation at 10:00 UTC, compatible with Vercel Hobby. Vercel sends this secret automatically. Existing Supabase app environment variables are reused; never expose server keys with `NEXT_PUBLIC_`. More frequent closed-app polling requires an appropriate Vercel plan/scheduler. Open-app polling works without this secret.
3. Each user opens [Whatnot Seller Dashboard → Developer → Tokens](https://www.whatnot.com/dashboard/developer?tab=tokens), creates a PAT limited to **`read:orders`, `read:shipments`, `read:shows`, `read:reports`**, and pastes it into **Thrift Log Settings → Whatnot → Connect & import read-only**. Only the Whatnot seller-account owner can create a PAT. Choose an expiry and replace the token in Settings when needed. The app verifies the seller identity, USD currency and four read capabilities before saving the encrypted token. A seller can have only one active Thrift Log workspace connection.
4. For complete seller fees and shipping costs, generate the desired historical **seller financial reports in Whatnot** (preferably before the initial import so available purchase costs enter the original sale), then refresh the connection. Thrift Log reads completed reports; it does not generate them because that needs `write:reports`. Sales without these charges are imported with profit clearly marked incomplete, rather than reporting guessed profit.

An extra encryption environment variable is optional: without it the app derives a domain-separated key from the existing service-role key. To make encryption independent of service-role rotation, set **`WHATNOT_TOKEN_ENCRYPTION_KEY`** to a securely generated 32-byte key encoded as 64 hexadecimal characters **before connecting accounts**. Changing this key, or rotating the service-role key when using the default derivation, requires affected users to reconnect and re-save any optional webhook signing secrets. Never put PATs, webhook secrets or encryption keys in source control, URLs or chat.

Migration application remains an explicit operator step. Do not replay existing migrations or run a blanket push against production without checking its history. To disable the feature safely, disconnect accounts or roll back application code; keep additive tables and imported records. Dropping tables is unnecessary.

## Matching holds and purchase costs

Old matching-only order holds are automatically reprocessed in batches of 20 during normal authorized sync. No per-item duplicate decisions are required. Genuine totals/refund/currency or giveaway-cost exceptions remain visible. Settings also provides Select all orders / Import selected, exact-cent pending purchase-cost entry and actionable partial results. See [import and saved-cost setup](IMPORT_REVIEW_AND_PURCHASE_COSTS.md); only saved-sale cost corrections require the new optional migration.

## What sync does

- Reads all accessible historical pages, then repeatedly reconciles them, using durable cursors, bounded requests, retries and seller-aware rate pacing. Backfills can take multiple continuations; Refresh resumes progress rather than starting an independent import.
- Uses exact external order/unit/ledger identifiers and tenant-scoped deterministic IDs. Retrying, overlapping reports, reconnecting the same seller and receiving a webhook twice do not create another sale or financial posting. Previously imported manual sales with the same Whatnot order ID can be adopted only when their physical pieces, prices and coupon reconcile.
- Reuses exact available inventory matches (SKU, explicit physical ID or linked marketplace product/variant ID). Similarity, ambiguity and reused/already-sold SKU matches do not hold imports; if there is no single available exact match, the source unit becomes a separate physical item. Optional explicit inventory linking remains available. New unmatched physical units receive stable internal IDs. Existing inventory cost is preserved; report cost conflicts require review. Repeated SKUs do not mean multiple sales of one physical item.
- Imports actual order merchandise proceeds and coupons. Buyer tax and platform-collected shipping are excluded from seller income. Purchase cost from the financial report is used only where a physical unit can be identified; missing cost remains unknown, distinct from confirmed zero. For new historical items, unknown acquisition dates use a labeled sale-date storage placeholder, never claimed as purchase history.
- Posts reconciled commission/processing charges (including their tax) and seller shipping on the report's actual ledger dates through the existing immutable event model. No double allocation of shared shipment charges. Existing financial records are never silently rewritten.
- Advances the existing fulfillment state only when the provider confirms handover/in-transit/delivery; creating a label is not shipping. It preserves known handover dates and does not invent dates from generic update timestamps or infer a backward move from a replacement label. Existing manually grouped packages are preserved. Buyer addresses are not imported.
- Imports show identity, scheduled/actual start and available live duration, linking orders to shows. Whatnot viewer counts and estimated earnings appear separately from calculated business profit. A stopped show remains resumable. A cancelled show is marked ended locally to release reservations, with its cancelled source status retained. Durations beyond the current local 24-hour limit remain available in provider analytics without truncating them into a false local duration.
- Updates the existing workspace atomically with private source receipts/checkpoints, so dashboard, financial reports and inventory pipeline consume the same canonical records. A concurrent user save causes a safe retry against the latest revision.

While the authenticated app is visible, it checks status every minute and attempts reconciliation when due (normally five minutes); backfill continuations run sooner. A post-connect continuation starts the first few chunks. The configured daily cron works when the browser is closed and processes up to five due active users, with bounded round-robin continuations. Larger histories can require multiple runs or leaving the app open. Last successful full pass, attempt time, progress, review count and sanitized errors are visible in Settings. Missing migrations, expired credentials, unavailable scopes and provider failures have distinct messages. Revoking beta access blocks foreground, scheduled and webhook commits immediately.

Disconnect deletes the stored PAT and signing secret and invalidates in-flight leases; imported records remain. It does not revoke the external PAT: revoke it in Whatnot's token dashboard if desired. Switching sellers requires disconnect first. No Whatnot products, listings, orders, shows or reports are modified by this app.

## Optional signed webhooks

Polling is sufficient to connect. For faster notifications, if your Whatnot developer app has webhook access:

1. Connect the account first. Open the optional webhook section in Thrift Log Settings and copy that workspace's HTTPS endpoint.
2. Configure the documented order/show/shipment events in the Whatnot developer dashboard. The official spec provides no REST endpoint for creating subscriptions.
3. Paste the dashboard's `wn_wh_…` signing secret into the private signing-secret field in Thrift Log.

The receiver verifies Standard Webhooks HMAC over the original body, event ID and timestamp (five-minute tolerance), checks seller/connection identity and current beta access, and durably deduplicates before acknowledgment. It requests a fresh authoritative API reconciliation; webhook payloads never directly post money. Delayed, out-of-order or missed notifications are covered by polling. Delivery IDs expire from the dedupe table after 30 days, while source/entity IDs and postings remain idempotent.

## API and accounting limits

- **USD only.** No conversion or mixed-currency accounting is fabricated.
- **Bank payouts:** the verified Seller API has no payout-transfer/settlement endpoint. Payout records and cash reconciliation remain manual; net seller earnings are not treated as payouts.
- **Refunds:** financial reports expose net seller refund activity without a reliable structured gross refund/fee-credit split. It is imported for review. Enter actual customer refund, fee credit and shipping adjustment; their integer-cent net must reconcile exactly before dated postings are saved. No physical inventory return is inferred. Unsupported appeal credits, tips or unallocated positive carrier credits remain visible for manual reconciliation, rather than inventing their accounting meaning.
- **Reports:** only completed reports already accessible to the token are read. Downloads are bounded (10 MB, 20,000 rows), credential-free HTTPS from allowlisted Whatnot/cloud-storage hosts, with redirects rejected. A newly introduced official report host/format may require an adapter update. No raw buyer/contact data or expiring report URLs are stored. Changed previously posted ledger IDs are flagged for dated correction rather than silently reapplied.
- **Order exceptions:** unsupported tax-inclusive prices, missing identity/date, contradictory totals, unresolved shows, mixed/reused physical matches and orders over 30 physical units require review/manual correction. No paid sale is invented for unpaid/failed orders. Report evidence is required to book cancelled orders with historical earnings. Source records are retained for recovery.
- **Cost corrections:** an already posted sale's cost basis remains immutable. Later report arrival does not rewrite a previously unknown COGS amount; unknown profit stays incomplete. Enter available source costs before initial posting when possible, or use an explicitly audited correction process. A generalized historical COGS-backfill editor is not introduced here.
- **Credential scope:** the app verifies read endpoint access and executes only fixed, allowlisted GET operations. PAT introspection is not documented, so the UI cannot prove whether a supplied token also carries unused write scopes. Create it with the four narrow scopes above. Token expiry/refresh is managed by replacement, not an invented refresh endpoint.
- **Live verification:** seller eligibility, a real token, actual report-download host/content, webhook subscription permissions and production migration readiness cannot be verified without account authorization. Physical iPhone acceptance remains manual; automated mobile tests use iPhone-sized Chromium.

## Security and verification

The three integration tables have RLS enabled, no anon/authenticated policies or grants, and no client-visible credentials. Only the server service role can call the integration RPC. Foreground routes validate origin, fresh Supabase Auth and current beta membership, and derive tenant IDs from the session rather than request data. The RPC rechecks membership, and every record lookup includes tenant and seller identity. Existing business tenant foreign keys, atomic revision checks, immutable ledger rules, photo policies and workspace access checks remain in force. Tokens use randomized AES-256-GCM with tenant/provider/purpose authenticated data, are never returned to clients, and are not stored in browser storage. Logs/errors do not include upstream response bodies or secrets.

The test suite includes synthetic official-shaped contracts, API allowlists/pagination/retries, encrypted credential boundaries, signature verification, exact-cent financial reconciliation, missing-fee and unknown-cost guards, inventory matching, idempotent source updates, resumable sync, disconnect races, signed webhook replay, real local PostgreSQL RLS/RPC/atomic rollback, schema-6/7 owner preservation, and desktop/mobile connection/review flows. Browser and database tests use isolated doubles/PGlite, never a production project. Existing AI imports, registration, photo isolation and pipeline tests remain part of the regression suite.
